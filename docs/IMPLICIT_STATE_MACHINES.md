# State lifecycles in ScaleSquad

Reviewed and remediated **2026-11-14**, current working tree. The original audit identified **73 stateful flow families**, not 73 confirmed defects. **29 families were hardened; 44 retain their existing guarded or delegated owner.**

Numeric counters, request identity and clocks are context. Flags can be parallel axes, especially notification permission and subscription state. Not every listed label is a mutually exclusive enum.

## Scope and evidence

Owned web, Flutter, backend, transport, PWA and simulator code was reviewed. The refreshed structural graph covers 166 source files, 806 nodes and 1,427 edges. Every inventory row below has a refreshed source anchor. Runtime checks and their limits are recorded in [the verification report](STATE_LIFECYCLE_VERIFICATION.md). This is not proof of all possible interleavings.

Normal game phases already have an explicit transition table in `matchStateMachine.ts`; the simulator already has a pure `step` transition. Their game rules were preserved. Small selectors, framework navigation/animation, browser worker events, counters and bounded queues retain their appropriate owners rather than gaining redundant reducers.

Native authentication, live gameplay, chat and push remain planned. Voice remains disabled. SDK/browser internals are excluded; the chat adapter now observes the installed SDK connection handler.

## Fixes and invariants

- Match identity, request lifetime and revision ordering all gate publication; accepted commands are distinct from follow-up reads.
- Notification permission, browser endpoint and server confirmation are separate. Failed rollback remains visible and retryable.
- Chat reconciliation intents survive process restart and precede remote provisioning/member work. Ready/start cannot bypass pending member repair.
- Run transitions share one begin/settle owner; complete means all results in the stage are stored. Partial retry validates and reuses immutable saved results.
- Socket timers, worker settlement and shutdown each have one owner. Native startup has an explicit reduced-motion bypass.

## Complete disposition

Hardened means code changed to address an identified lifecycle risk. Retained means source review found an existing suitable owner/guard; it does not claim a dedicated new runtime test for every row.

## Remaining boundaries

- A timeout or cancelled browser request cannot prove that a remote mutation did not commit. Confirmed outcomes and durable compensation are retained; unknown outcomes require reconciliation. No distributed transaction is claimed.
- Reconciliation uses the existing single-server membership queue and version-checked task deletion. Multi-process coordination is outside the current deployment model.
- A provider must confirm removal for a cleanup record to be discarded. Unknown/already-absent provider errors are retained for retry rather than guessed to be success. Live configured-provider delivery was not established by isolated tests.
- Browser permission prompts and subscription APIs are browser-owned and cannot all be cancelled. Optional logout cleanup is bounded; newly created endpoints are rolled back on failed registration where the browser permits it.
